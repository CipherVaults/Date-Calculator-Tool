2. WRONG (build plan section 12, smoke test): 'weekend friSat changes the count' for US preset 2024-01-01 -> 2024-01-31 cannot pass. January 2024 starts on a Monday, so 31 days = 4 full weeks + Mon/Tue/Wed. Sat/Sun gives 4 Sat + 4 Sun = 8 weekend days and Fri/Sat gives 4 Fri + 4 Sat = 8. New Year (Mon Jan 1) and MLK (Mon Jan 15) are working days under both weekends. Both weekends therefore give 21 business days with the end included and 20 without. Use a range where the counts differ, e.g. 2024-01-01..=2024-01-05 (satSun 4 vs friSat 3), and pin exact expected numbers (US Jan 2024: 20 exclusive / 21 inclusive).

## gaps
1. History field limits: the reference validate_history fields (I confirmed in commands.rs) require copy_text and every single-line field to be <= MAX_FIELD_LEN = 256 bytes. Several date-math copyTexts exceed this. Days-between with 0001->9999, end included, backward note is ~280 bytes. Age copyText with next birthday and leap note is ~300. Date-info copyText (12 lines) is ~300+. Business copyText with a holiday list can far exceed 256 and even MAX_COPY_LEN 4096 (up to 500 holidays). history_add/copy_text would reject these at runtime. The plan must either raise the history copyText limit (e.g. 1024) or cap the holiday list in copyText (e.g. first 10 + 'and n more'), and keep total copyText <= 4096 with a test at the max-length case.
2. Amount inputs: the plan uses <input type=number>. Its .value returns "" for unparseable content ('1,5', '1e', '--1'), and date-math treats blank as 0, so the UI silently computes with 0 instead of showing invalid_amount. type=number also blocks '-' on the iOS numeric keypad and accepts '1e3'. Use type=text inputmode=numeric plus the core parser. Optionally normalize Arabic-Indic (U+0660-0669, U+06F0-06F9) digits in the UI layer on both platforms for Egyptian users.
3. JS engine sandbox: node:vm runInNewContext({}) still provides Date, Intl and Math built-ins, so 'runs with no Date' is not enforced by vm alone. CI must delete or shadow Date/Intl in the context (e.g. run 'globalThis.Date=undefined; globalThis.Intl=undefined' first) in addition to the static regex.
4. Countdown offsets (date-math design): the UI recipe `new Date(y, m-1, d, ...)` maps years 0-99 to 1900-1999, so it must use setFullYear. For historical dates, Chrome/WebView2 getTimezoneOffset can return fractional LMT minutes (e.g. Cairo pre-1900 is about -125.15), which fails the integer utcOffsetMinutes deserialization. Round the offset, fall back to the offset of the current year, or restrict countdown target years. Nonexistent or ambiguous DST local times need a defined rule. The tick should align to the wall-clock second (setTimeout to the next boundary) to avoid skipped or duplicated seconds, and pause on visibilitychange (plan has this).
5. Accessibility (the reference has role=status aria-live=polite, role=dialog aria-modal aria-labelledby on the About/Install/Settings modals, aria-label on the quick-nav/history filter/mode group, :focus-visible, and the safe-area env() insets). None of the three specs carries these forward for the new UI. Needed: a live region for results; the countdown clock must NOT be aria-live (it would announce every second), so use a separate polite region updated on status change or each minute; mini-calendar cells need aria-label with full date + weekday + holiday name, or should be aria-hidden with the textual holiday list as the accessible source; weekend checkbox pills in a fieldset/legend; the leap-rule and include-end toggles labelled; focus return after modal close; 44px targets for calendar cells and ‹ › buttons on coarse pointers.
6. The leap-day-rule toggle (date-math Age mar1) and observedMode (holiday spec) have no place in the plan's UI or settings schema. The plan's firstDayOfWeek is not in either spec.
7. Warning and flag fields are missing from the result schemas: presetYearOutOfRange, usedApproximateHolidays and per-holiday approximate are not in the date-math BusinessDays/AddSubtract result field lists. The UI 'estimated (±1-2 days)' marker therefore has no data path, and parity would not cover it.
8. Backward ranges with includeEndDay: under date-math [lo,hiX) semantics, when end < start the toggle labelled 'include end day' actually includes the START input (the later date) and the end input is always counted. C4 (Jan 31 -> Jan 1, F) counts Jan 1 and excludes Jan 31. Either relabel ('include the later date') or define it relative to the input order, and add vectors for it.
9. 'today' handling: the plan says an empty Age asOf means today, but date-math returns missing_date for empty. Define that the UI substitutes local today and echoes it visibly. Midnight rollover is in the plan only. Date-info `today` and countdown `now` must be refreshed on rollover, and the smoke tests must never use real today (plan states this, date-math doesn't).
10. Hand-verified correctness vectors: the plan's golden.json is Rust-generated (a regression lock only) and it drops the date-math vectors.json of hand-verified expectations. The plan's holiday_tables.rs covers holidays, but section 12 date-math vectors (V/A/B/C/G/I/K) are not carried into any fixture in the plan.
11. UK preset gaps: the 1981-07-29 one-off is missing (see wrong vectors). Future proclamations need a release, and README/About must state the last verified year (e.g. 'UK one-offs verified through 2027').
12. Egypt: no Coptic Easter Sunday rule in the holiday spec (user asked for it). Egypt's practice of moving holidays to Thursday by decree is only documented, not modelled. Also needed: an in-UI 'how to correct' flow (exclude + custom one-off) next to the preset, and a hint to switch to the Fri/Sat weekend when Egypt is picked.
13. Custom holidays: date-math has no recurrence (yearly) and no enable flag. Desktop UI id generation, the 100/200 limit and the 60/64 name limit must be unified. CSP-safe rendering via textContent is in the holiday spec only. The plan's smoke check '<b>x</b> renders literally' is good, but there is no equivalent check in the mobile safety-eval Slice A list for the custom-holiday list in the settings modal (only names in results).
14. Settings robustness: with custom holidays in settings.json, a corrupt file resets everything (reference behaviour). Need a .bak or a separate holidays.json, a schemaVersion for future migrations (holiday spec has it, plan does not), and a mobile localStorage equivalent.
15. Business-day performance on mobile: per-keystroke live recompute over 300-year spans with Egypt Hijri expansion needs the per-year memo (date-math mentions it) and input debounce. The plan's per-day stepping with cap 100,000 conflicts with the Days max of 3,652,058.

18. Repo and publishing: making CipherVaults/Date-Calculator-Tool public with UNLICENSED source is an owner decision. The release job auto-publishes on the first green push to main, so release-notes-v1.0.0.md and the version-consistency check must exist before any merge.

The mobile favicon data URI must be covered by img-src data: (already present). The plan has no update-check fallback when the GitHub API rate-limits (the reference behaviour is copied verbatim, fine).
